TRD-v2.html 作为阶段一的技术方案文档，整体架构合理、技术选型务实。文档准确识别了当前代码的 8 个关键缺口，并提出了 4 个新增模块和 3 个修改模块的设计方案。

关键认知修正：原评审对 Scheduler-Executor 耦合、Credential 密钥管理、DevOps 接口抽象等问题的质疑，在 MVP 语境下是过度设计。阶段一的核心目标是"快速验证核心闭环"，而非追求架构完美。

3 · 修订后的问题清单

3.1 需要补充的设计细节（P1）

3.1.1 Issue → Task 字段映射设计缺失
P1 需补充

问题描述：

  • TRD §5.1 提到"DevOps 任务内容填充"，但未明确具体的字段映射规则
  • PRD US-D02 要求"展示完整内容（描述、验收标准、相关链接）"，但未说明如何映射到 Task 模型
  • 用户编辑能力的技术实现方式未说明

影响分析：

  • 前端无法确定哪些字段可以预填、哪些需要用户手动填写
  • Task 模型的字段设计可能遗漏关键信息
  • DevOps API 返回的数据结构与 Task 模型可能存在差异

建议补充：在 TRD §5.1 或 §7 中增加字段映射表，明确：

DevOps Issue 字段Task 模型字段映射方式是否可编辑
issue.titleTask.name / devops_title直接映射可编辑
issue.descriptionTask.devops_body直接映射可编辑
issue.repo_urlTask 参数或 resolved_config提取后注入不可编辑
issue.branchTask 参数或 resolved_config提取后注入可编辑
issue.assigneeTask.creator_id当前登录用户自动填充
issue.labelsTask.params 或 tags转换为标签可编辑
issue.priorityTask.priority映射优先级枚举可编辑

同时说明：

  • 用户可以在创建任务时覆盖哪些字段
  • 覆盖后的值如何存储（params JSON？独立字段？）
  • Template 参数与 Issue 字段的优先级关系
3.1.2 "内层自检"的技术实现方式不明确
P1 需澄清

问题描述：

  • PRD §2.3 和 TRD §1.3 都提到"内层自检（始终生效）"
  • 补充说明指出"不存在内外层自检，这应该是研发 Agent 的 SOP"
  • TRD 未说明如何将 Template 定义的 success_criteria 转化为 Agent 可执行的 SOP

概念澄清：

根据补充信息，正确的理解应该是：

  • 不是平台层面的"内层/外层"两个独立检查机制
  • 而是Agent 在执行过程中的标准操作流程（SOP）：
    1. 编码完成后，按 Template 定义的 success_criteria 执行自检
    2. 自检不通过 → 修复 → 重新自检（Agent 内部循环）
    3. 自检通过后 Push 代码
    4. （未来）通过 MCP Server 获取 CI/CD 结果，失败则修复重推

TRD 需要明确的要点：

  • Template → Agent 指令的转换：success_criteria 如何传递给 Agent？（系统提示？环境变量？配置文件？）
  • 自检命令的执行方式：调用项目已有测试命令？执行 lint 工具？检查特定文件？
  • SOP 循环的控制逻辑：在 Wrapper 侧还是 Agent SDK 侧实现？如何避免无限循环？

建议补充：在 TRD §5.1 或新增章节说明 Agent SOP 的技术实现机制，包括：

  1. Template success_criteria 如何渲染为自然语言指令
  2. 通过 Wrapper 的哪个接口触发自检命令
  3. 如何捕获和解析执行结果（不同测试框架输出格式各异）
  4. SOP 循环的控制参数（超时、最大轮次、退避策略）

3.2 已确认合理的 MVP 简化策略

基于补充的决策记录，以下在原评审中被标记为"问题"的内容，实际上是合理的 MVP 简化：

3.2.1 Scheduler 消费循环的设计（原 P0 问题）
已接受 MVP 简化

原评审观点：Scheduler 与 Executor 紧耦合违反架构原则

修正后的理解：

  • TRD §4.2 提出的"dispatchLoop 调用 executor.Execute()"是MVP 阶段的合理简化
  • 虽然理想架构应该是解耦的消费者模式，但阶段一的目标是快速验证核心闭环
  • 决策记录明确"复用已有代码"是核心原则，强行解耦会增加不必要的复杂度

评审结论：接受当前设计。MVP 阶段可以采用紧耦合，后续重构为事件驱动即可。

建议：在 TRD 中增加注释说明"此为 MVP 简化方案，v1.2 将重构为独立的 Consumer 服务"。

3.2.2 Credential Manager 密钥管理简化（原 P1 问题）
已接受 MVP 简化

原评审观点：缺少密钥轮换和过期策略，安全风险较高

修正后的理解：

  • 明确说明"MVP 阶段可以简化"
  • 阶段一只服务于内部小团队，密钥泄露风险可控
  • AES-256-GCM 加密本身是安全的，主要风险在于密钥存储方式

评审结论：接受当前设计。MVP 阶段采用配置文件存储密钥是可接受的。

建议：在 TRD §9 安全设计中增加"MVP 限制说明"：

  • "阶段一采用配置文件存储加密密钥，适用于内部可信环境"
  • "生产环境部署前需评估集成 KMS 或 Vault 的必要性"
  • 至少确保密钥不在版本控制系统中（通过环境变量或 .gitignore 保护）
3.2.3 DevOps Integration 抽象层（原 P1 问题）
已接受 MVP 简化

原评审观点：接口设计过于简化，无法覆盖多平台适配

修正后的理解：

  • 决策记录明确"任务来源是 DevOps 平台的任务管理（非 GitHub Issue）"
  • 阶段一只需要对接一个 DevOps 平台（京东行云）
  • 不需要考虑多平台适配的复杂性

评审结论：接受当前设计。针对单一平台优化接口是务实的选择。

建议：在 TRD §4.3 中明确标注"阶段一只支持京东行云平台"。如果未来需要支持其他平台，再考虑插件化架构。

3.2.4 双 Runtime 切换（原 P1 问题，调整为 P2）
待确认 优先级调整

原评审观点：Docker 和 K8s Runtime 接口不兼容，技术可行性存疑

修正后的理解：

  • 决策记录显示"本地 Docker + 远程 K8s 双运行时"
  • 但这可能是长期目标，不一定是阶段一的强制要求

评审结论：需确认优先级。如果阶段一必须支持双 Runtime，则需要先统一接口定义；如果可以先只支持 Docker，K8s 推迟到 v1.1，则当前方案可接受。

建议：在 TRD §8 中明确阶段一的 Runtime 支持范围。
