原 P0-1 多租户 + 原 P0-2 模板系统 — 已解决

原问题：TRD 保留了多租户体系和模板系统，与旧版 BRD "无多租户""无模板系统"矛盾。

残留建议：TRD 应补充一句说明 tenant 在一阶段的处理（后端自动填默认值，前端不暴露），避免开发者困惑。

P1 方案缺失或过度设计

P1-1 DevOps MCP Server 集成方案过于粗略

对照 BRD §3.2 "CI/CD 反馈闭环" + PRD §3.2 "双层反馈闭环"

问题：TRD §4.3 DevOps Integration Service 只定义了四个接口（ListTasks / GetTaskDetail / CreateMR / GetRepoInfo），但 BRD 和 PRD 的核心卖点之一是"双层反馈闭环"（内层自检 + 外层 CI/CD via MCP Server）。TRD 没有回答：

  • MCP Server 如何集成到沙箱内？是 Wrapper 启动时注入 MCP Server 地址？还是 Agent CLI 自带？
  • CI/CD 结果如何传递给 Agent？MCP Server 是被 Agent 主动调用，还是推送通知？
  • 修复循环上限（默认 5 次）放在哪里执行——Agent 内部、Wrapper、还是控制面？
  • TRD 的 DevOpsService 只设计了控制面侧的 API（拉取 Issue、创建 MR），但沙箱内 Agent 如何通过 MCP 获取 CI/CD 结果完全没有设计

影响：这是"外层闭环"能否跑通的关键。如果 TRD 不定义 MCP Server 的集成方式，开发时只能靠猜测。

建议：TRD 应增加一节描述沙箱内 MCP Server 的集成方案——至少包括：MCP Server 的部署位置、Agent 如何发现和调用、CI/CD 结果的数据结构、修复循环的控制点。

P1-2 任务创建 API 缺少从"浏览任务列表"到"创建"的完整交互路径

对照 BRD §3.1 "平台对接 DevOps 平台的任务管理" + brainstorming "平台直接调 DevOps API"

问题：TRD §6.1 API 定义了 GET /devops/tasks（拉取列表）和 POST /tasks（创建任务），但缺少两者之间的交互设计：

  • 用户在 UI 上看到 DevOps 任务列表后，点击某个任务，前端调什么 API？只传 devops_task_id？还是需要前端补填 repo_url / branch？
  • POST /tasks 的请求体仍有 repo_url、branch、overrides 等字段——如果这些可以从 DevOps 任务详情自动获取，前端不需要传
  • 缺少"选择模板"的交互——brainstorming 决策和 PRD 都要求创建时选模板，但 API 没有体现模板选择的流程

建议：TRD 应补充一条完整的 API 调用序列：GET /devops/tasks → 用户选择 → GET /devops/tasks/:id（获取详情含 repo/branch）→ 用户选模板 → POST /tasks（只传 devops_task_id + template_id，其余由后端补全）。

P2 方案不完整或存在隐患

P2-1 状态机方案与 BRD 不一致

对照 BRD §3.3（7 状态）+ 代码 model/task.go（9 状态）

问题：BRD 明确去掉 WaitingApproval 和 Retrying，简化为 7 个状态。但代码中仍然保留了这 9 个状态常量，TRD 没有说明如何处理：

  • TRD §3.2.2 状态机图确实只画了 7 个状态——但 §7 数据模型变更没有提到删除或废弃 waiting_approval 和 retrying
  • TaskService 的 validStatusTransitions map 仍然包含 WaitingApproval 和 Retrying 的转换规则
  • Executor 的 canExecute 方法仍然允许 Retrying 状态的任务执行

影响：方案和代码不同步，后续维护会混乱。如果代码保留了这些状态，迟早会有人使用它们。

建议：TRD §7 应明确标注一阶段废弃的状态，并给出代码层面的处理方式（注释掉、返回 unsupported、或加 // deprecated 标记）。

P2-2 缺少 DevOps 任务 → Task 的字段映射设计

对照 BRD §3.1 + brainstorming "任务来源：DevOps 平台的任务管理"

问题：用户在 UI 上选择一个 DevOps 任务后，系统需要把任务信息预填到 Task 创建表单中。但 TRD 没有定义哪些字段自动预填、哪些需要用户手动补充。

建议：TRD 增加一张字段映射表，定义 DevOps 任务字段到 Task 字段的预填关系（标题→Name、正文→Description、仓库/分支自动填充等），并标注哪些字段允许用户编辑覆盖。保持简单——就是预填 + 可编辑，不需要复杂的 Resolve 流程。

P2-3 Scheduler Dispatcher 方案的健壮性不足

对照 TRD §4.2 + 代码 scheduler.go

问题：TRD §4.2 设计了一个每秒轮询的 dispatchLoop，但有几个健壮性隐患：

  • 无退避策略：Dequeue 返回空（队列空）时，1 秒后立即重试。生产环境下持续空轮询会浪费 Redis 连接。应加指数退避或 BLPOP。
  • 无并发控制：dispatchLoop 是单 goroutine，但 Dequeue → RateLimiter → Execute 之间没有事务保证。如果 Execute 失败，任务已出队但未执行，会丢失。
  • Executor 执行是同步的：s.executor.Execute(ctx, task) 在 dispatchLoop 内同步调用。如果 Execute 阻塞（比如 Docker 创建慢），整个调度循环会被卡住。

建议：Execute 应该在独立 goroutine 中执行（或至少带超时），调度循环不应被单个任务的执行阻塞。空队列时应加退避（比如连续 N 次空队列后 sleep 5s）。

P3 改进建议

P3-1 "内层自检"不需要 TRD 单独设计方案——它是 Agent 的 SOP

原标注：PRD §3.2.1 · 用户反馈：不存在"内外层"，自检就是 Agent 的标准操作流程

调整：原评审认为"TRD 缺少内层自检方案"。实际上 Agent 的编码→测试→lint→修复循环就是 Agent 自身的工作流程（SOP），不需要 TRD 额外设计方案。TRD 只需要关注 Template 的 success_criteria 字段如何传递给 Agent 作为自检标准即可——这已经在 TRD §5.1 Template Spec 中定义了。

结论：从评审列表中移除，不构成问题。

P3-2 Credential Manager 缺少轮转和过期策略（MVP 阶段可简化）

TRD §4.4 描述了凭证的存储和注入，但没有提到凭证过期怎么办、用户更新 Token 后如何刷新。MVP 阶段可以简化为：每次创建沙箱时重新获取最新凭证（即读即用、不缓存）。建议 TRD 加一句说明 MVP 策略即可。

P3-3 Wrapper 与 Agent SDK 的集成方案引用 ADR-002 但未纳入正文

TRD 多处提到"基于 ADR-002 Agent SDK 集成决策"，但 ADR-002 在 design-book.html 的附录里，不在 TRD 正文中。读者需要跳转两个文档才能理解完整方案。建议至少在 TRD 中概述 ADR-002 的核心决策（单进程双循环、协作式暂停）。

P3-4 缺少"开发者"到"user"的身份模型设计

BRD 说一阶段只有"开发者"，但 TRD 的 Auth Middleware 设计是 API Key → User → Tenant。一阶段需要几个 User？每个开发者一个？还是共享一个？User 和 Task 的关系（CreatorID）在一阶段如何初始化？这些应该明确。
