1 · 产品定位

Agentic Coding Platform 是一个面向开发者的 AI 编码任务执行平台。

开发者领取一个拆分好的 Issue，平台调度 Agent 在隔离沙箱中自动完成编码、测试、提交 PR。开发者只需 Review。

Issue in, PR out.

1.1 核心差异化

对比维度直接用 Claude Code CLI本平台
执行环境本地机器隔离沙箱，不影响本地
并发能力一次一个多任务并行
可观测性终端日志Web 实时日志、状态追踪
团队协作无多人共享、干预记录
成本管控无限制Token 上限、资源配额

1.2 目标用户

开发者——不是平台管理员，不是运维人员。

一阶段只有一个角色：开发者。开发者自己创建任务、自己看日志、自己干预、自己 Review PR。

管理面板、多租户、运维角色等平台能力推迟到二、三阶段。

2 · 三阶段演进

🚀 阶段一：单 Agent 编码闭环
目标：开发者领 Issue → Agent 自动执行 → 提 PR。能跑起来，用户能用起来。
能力说明
Issue → Task开发者在 Web 上填写 Issue URL 或粘贴内容，一键创建任务
代码仓库 CloneAgent 自动 clone 指定仓库和分支
Agent 执行闭环编码 → 自测 → 自检 → 修复，内部循环直到达标
实时日志WebSocket 推送 Agent 的执行过程
人工干预暂停 / 恢复 / 注入指令 / 取消
提 PRAgent 完成后自动创建 PR，通知开发者
本地一键启动make local 零依赖启动完整环境

不包含：模板管理、多租户、知识沉淀、CI/CD 集成、审批断点、多 Provider 选择。

⚡ 阶段二：AI Coding Team 基础设施
目标：支撑 AI Coding Team 的多 Agent 协作场景，满足 coding team 在通信、数字员工持久化方面的需求。
能力说明
多 Agent 角色Product / Architect / Developer / Tester 等角色
Manager 星形拓扑Manager 作为唯一通信枢纽，Worker 之间不直接通信
Inbox 投递每个 Agent 有独立 inbox 目录，Manager 投递任务
持久化 AgentManager 从 Job 升级为 Deployment，长期运行
三层日志L1 人类信号（永久）、L2 任务指标（90 天）、L3 调试步骤（30 天）
知识蒸馏所有角色可写入结构化知识（knowledge_distill 工具）
越权防护文件路径沙箱 + 工具访问控制 + 状态机约束

不包含：多租户、模板 DSL、DAG 编排。

🌐 阶段三：多业务 Team 扩展
目标：将平台能力开放给其他业务团队（运维、分析、内容等），成为通用 Agent 任务基础设施。
能力说明
多租户 & 配额资源隔离、配额管理、数据隔离
YAML DSL 模板完整的任务定义模板（五大模块）
DAG / 动态编排静态依赖编排 + Agent 动态编排
多 ProviderClaude Code / 智谱 GLM / DeepSeek / 自定义
管理面板租户管理、能力注册、资源监控
知识应用历史案例检索注入新任务上下文
CI/CD 深度集成多流水线支持、部署状态追踪、自动回滚

3 · 阶段一功能需求

3.1 任务创建

需求说明
任务来源平台对接 DevOps 平台的任务管理，展示用户的待办任务列表，开发者从中选择并启动任务
任务定义DevOps 任务标题作为任务目标，正文作为详细描述。创建时选择预置模板（编码任务/Bug 修复/代码重构），模板定义成功标准
一键启动确认后系统自动创建沙箱、clone 代码、启动 Agent，无需开发者手动配置环境

3.2 任务执行

需求说明
独立沙箱每个任务创建独立的沙箱实例，任务完成后实例销毁。多个任务各自独立运行，互不干扰
自主执行Agent 在沙箱中自主完成编码、提交代码
CI/CD 反馈闭环Agent 提交代码后，通过 DevOps MCP Server 获取应用 CI/CD 的执行结果（测试、扫描、构建等）。发现问题后自动修复并重新提交，形成 提交→CI/CD→反馈→修复 的闭环
资源限制每个任务有 Token 上限和执行时长上限（默认 30 分钟），超限自动终止

3.4 任务管理

需求说明
任务列表展示用户的所有任务及当前状态（待调度/执行中/已完成/失败/已取消）
任务状态实时获取每个任务的执行状态和进度
暂停暂停正在执行的任务
恢复恢复已暂停的任务继续执行
关闭终止任务并清理沙箱资源
注入指令向运行中的 Agent 注入额外指令，用于纠偏或补充指导

3.5 执行可观测性

需求说明
实时日志通过 WebSocket 实时推送 Agent 的执行过程
状态追踪任务状态变更实时推送
资源监控展示 Token 消耗、执行时长
历史记录支持查看已完成的任务列表和执行日志

3.6 交付与通知

需求说明
自动提 PRAgent 完成后自动向目标仓库创建 Pull Request
完成通知任务完成（成功或失败）后通知开发者
干预通知Agent 遇到异常或需要人工介入时通知开发者

3.7 产品形态

形态说明优先级
API 服务RESTful API✓ 核心
用户面板Web UI（创建任务、查看日志、干预操作）✓ 核心
本地开发make local 一键启动（SQLite + miniredis + Docker）✓ 核心
管理面板—✗ 不需要
CLI 工具—✗ 不需要

3.8 一阶段约束

约束说明
单 Provider只支持 Claude Code CLI，不提供 Provider 选择
单 Agent每个任务一个 Agent，不支持多 Agent 协作
FIFO 调度简单队列，不支持优先级、抢占
DevOps 集成通过已有的 DevOps MCP Server 获取 CI/CD 反馈，不需要平台自建流水线
预置模板保留模板体系（3 个预置模板：编码任务、Bug 修复、代码重构），不支持自定义模板。模板定义成功标准（lint 通过、测试通过率等）
单租户运行一阶段不暴露租户概念，数据模型预留多租户字段。所有用户平等使用，不做资源隔离
本地优先支持 make local 零依赖启动，降低开发者上手门槛

4 · 非功能需求

4.1 性能

指标目标
API 响应< 200ms
任务调度创建后 10s 内开始执行
并发任务单实例支持 5 个并行任务
日志延迟WebSocket 推送 < 1s

4.2 可靠性

指标目标
Agent 心跳5s 间隔，15s 超时
任务超时默认 30 分钟，可配置
沙箱清理任务完成 1 小时后自动清理

4.3 安全

维度方案
认证API Key（一阶段）
沙箱隔离Docker 容器隔离，禁止跨任务访问
密钥管理API Key 不在日志中输出
审计所有操作记录审计日志

4.4 可观测性

维度方案
执行日志实时流式输出 + 持久化存储
状态追踪任务状态变更实时推送
资源监控Token 消耗、执行时长

5 · 术语表

术语说明
Task一次 Agent 执行的抽象单元
Sandbox任务运行的隔离容器环境
Agent执行编码任务的 AI（一阶段即 Claude Code）
Issue代码仓库中的任务单元（Git Issue）
PRPull Request，Agent 的交付产物
ProviderAgent 运行时的配置抽象（一阶段只有 Claude Code）
Intervention人工干预操作（暂停/恢复/注入/取消）
Wrapper沙箱内的 Agent 管理进程（HTTP Server + SDK）

6 · 与旧版 BRD 的关键变更

维度v0.5（旧）v1.0（新）变更理由
目标用户开发者 + 管理员 + 运维一阶段只有开发者聚焦，先让开发者用起来
MVP 范围模板 + 多租户 + 能力注册 + Provider 管理Issue → Agent → PR 一条线砍掉非必要，加速落地
反馈闭环未明确 CI/CD 反馈路径通过 DevOps MCP Server 获取 CI/CD 结果，Agent 闭环修复复用已有 DevOps 基础设施
状态机9 个状态7 个状态简化，一阶段用不到
模板系统YAML DSL 五大模块不需要一阶段 Issue 就是任务定义
知识沉淀四种类型 + 自动入库不需要推迟到二/三阶段
Provider三层作用域 + 多 Provider单 Provider（Claude Code）一阶段不需要选择

7 · 开放问题

  • DevOps 任务 → Task 的映射规则：任务标题作为任务目标，正文作为详细描述？是否需要开发者补充修改？
  • Agent 自测策略：如何判断"达标"？预置模板定义了 lint 通过、测试通过率等标准——是否足够？
  • MR 通知方式：Web 推送？邮件？IM？一阶段只做 Web 推送是否足够？
  • 并发上限：单实例 5 个并行任务的依据？是否需要可配置？
  • 本地开发体验：Docker 不可用时任务执行会失败——是否需要 mock 模式让开发者可以先体验 UI？
