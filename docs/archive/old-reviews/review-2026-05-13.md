# Agent Infra 架构评审 — 2026-05-13

**评审范围**：BRD v0.5 + PRD v0.8 + TRD v2.5（design-book.html）+ 核心代码实现  
**评审人**：AutoClaw

---

## 🔴 P0 — 必须修复（功能缺陷 / 安全风险）

### 1. 认证完全缺失
- `router.go` 所有 `/api/v1/*` 路由没有 auth middleware，只有 health check 公开
- TRD 写了"API Key 认证 + RBAC"，实际代码里只有 `internal_auth.go`（wrapper 回调用），用户侧 API 裸奔
- 任何拿到地址的人都可以创建任务、删除租户、注入指令

### 2. 状态转换校验不完整——Failed 状态不允许重试
- `task_service.go` 的 `validStatusTransitions` 把 Failed 设为空数组（终态），但 TRD §6.3 明确写了 failed → retrying → running
- BRD 状态机图里也有这条路径，代码堵死了

### 3. Scheduler 没有 polling loop
- `scheduler.Start()` 只设了 `running = true`，没有后台消费循环
- `Dequeue()` 需要外部主动调用，但 `main.go` 没有启动任何 goroutine 调用 Dequeue → Execute
- 任务入队后永远不会被执行

### 4. API Key 存储不安全
- `api_key.go` 的 `key_hash` 没有看到 salt/argon2/bcrypt 配置
- 如果只是简单 SHA256，预计算攻击风险很高

## 🟠 P1 — 架构问题（设计-实现不一致 / 可靠性风险）

### 5. Model 与 DDL 严重不一致
- `model/task.go` 只有 ~10 个字段，DDL tasks 表有 30+ 字段（resolved_spec、pod_name、retry_count 等）
- GORM AutoMigrate 以 model 为准，大量 DDL 字段不会建出来
- resolved_spec、pod_name 等核心执行字段在 DB 里不存在

### 6. Executor 与 Scheduler 没有串联
- `main.go` 创建了 scheduler 和 executor，但两者完全独立运行
- 没有 "scheduler Dequeue → executor Execute" 的桥接代码
- TRD §3.3 写了调度→执行的完整链路，实际缺这一环

### 7. 模板 Spec 解析 / Resolver / Renderer 未实现
- TRD §4.3 定义了 TemplateSpec → Parser → Resolver → Renderer 管线
- `template_service.go` 只有基础 CRUD，没有 spec YAML 解析、Go template 渲染、Provider 合并
- 模板功能是空壳，无法生成执行配置

### 8. 心跳超时后无自动处理
- `HeartbeatManager` 检测到超时只更新内部状态，没有回调通知 executor/task_service
- TRD §5.4 写了"心跳停止 → 控制面标记异常"，代码里超时是静默记录
- 任务永远卡在 Running

### 9. Intervention 事件处理没有闭环
- `interventionService.Pause()` 先写 DB 再调 executor，如果 executor 端失败，DB 状态已经是 applied
- 缺少补偿/回滚逻辑

## 🟡 P2 — 设计问题（设计文档自身的矛盾 / 遗漏）

### 10. TRD 版本声明不一致
- design-book.html 标题写 "TRD · MVP"，但包含 v1.1/v1.2/v2.0 内容
- 微服务拆分路径和发布计划的版本边界模糊
- 建议：TRD 只写 MVP 范围，v1.1+ 写到演进文档

### 11. Provider 多租户隔离不完整
- `providers` 表用 scope + tenant_id + user_id 做 UNIQUE KEY，但 API 路由没有 tenant 隔离
- `task_service.Create()` 不校验 provider_id 是否属于当前租户

### 12. 没有速率限制 / 并发保护
- TRD 写了限流器，但 `router.go` 没有 rate limit middleware
- 任何人可以无限频率调 POST /api/v1/tasks

### 13. WebSocket 没有认证
- TRD §7.3 写了 ws://?token=api_key，但 `ws_handler.go` 没有 token 校验
- 任何人可以订阅任何 tenant 的任务事件

### 14. 缺少优雅重试策略
- DDL 里 max_retries DEFAULT 3，但 task_service 和 scheduler 都没有重试调度逻辑
- 谁负责 Failed → Retrying → Running？TRD 没有明确，代码也没实现

---

## 🔵 P3 — 改进建议

### 15. 依赖注入太手动
- `main.go` 手动 wire 20+ 依赖，大量闭包回调
- 建议引入 wire 或 fx 做 DI

### 16. 文档碎片化
- docs/ 下多个版本 PRD/TRD 共存（BRD.md、PRD.md、v1.0-mvp/*、current/*、v1.1-cicd/*、design-book.html）
- 建议明确 canonical 文档，其余 archive

### 17. 缺少可运行的 E2E 测试
- 单元测试覆盖不错，但核心链路没有端到端验证

### 18. Wrapper Sidecar 是 Python，控制面是 Go
- TRD §5.2 写 "Sidecar: wrapper (Go)"，实际是 Python（FastAPI）
- 两套语言的构建/测试/部署流程完全不同

---

## 总结

| 级别 | 数量 | 核心问题 |
|------|------|---------|
| 🔴 P0 | 4 | 认证缺失、状态机断裂、调度器没跑起来、API Key 不安全 |
| 🟠 P1 | 5 | Model/DDL 不一致、Executor/Scheduler 断联、模板管线空壳、心跳无动作、干预无回滚 |
| 🟡 P2 | 5 | TRD 版本越界、多租户隔离、无速率限制、WS 无认证、重试逻辑缺失 |
| 🔵 P3 | 4 | 手动 DI、文档碎片化、无 E2E、Go/Python 双栈 |

**结论**：设计文档写得很完整，但实现覆盖面约 40%——CRUD 骨架在了，核心链路（调度→执行→反馈→重试）还没串通。最紧急的是补认证、接 Scheduler 消费循环、对齐 Model 和 DDL。
